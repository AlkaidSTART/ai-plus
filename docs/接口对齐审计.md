# 前后端接口对齐审计

审计时间：2026-09-15
审计范围：`frontend/src` 全部业务页面 / 组件 / composable / API client，对照 `backend/src/insightx/api`、`docs/api.md`。

## 1. 结论速览

**页面没数据的主因不是「后端缺很多接口」，而是三个叠加问题：**

1. **前端只接了 3 条 P0 接口**（创建任务、任务列表、SSE），后端已实现的「任务快照 / 取消 / 重试 / 报告 / 证据 / 健康检查」前端根本没写调用。
2. **前端多个模块本身就是静态占位页**（雷达 / VOC / 改款 / 财务），连后端已实现的列表接口都没接。
3. **后端执行链路未接入 Worker**，任务会长期停在 `QUEUED`，报告和证据不会产出真实数据；即使前端立刻接上 report / evidence，也只会拿到 `REPORT_NOT_READY` 或空结果。

**所以是「前端漏接已有接口」+「后端 P1/P2 能力确实未实现」，而不是「后端 P0 缺一大堆接口」。**

## 2. 后端实际接口（9 条，全部已实现）

统一前缀 `/api/v1`，资源命名以 `tasks` 为基线（不是 `insight/task`）。

| # | 方法 | 路径 | 响应 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | GET | `/api/v1/health` | 健康状态 | 前端未接 |
| 2 | POST | `/api/v1/tasks` | `TaskCreatedResponse` | 需 `Idempotency-Key` |
| 3 | GET | `/api/v1/tasks` | `Page<TaskListItem>` | 支持 `status/cursor/limit` |
| 4 | GET | `/api/v1/tasks/{task_id}` | `TaskSnapshot` | 前端未接 |
| 5 | POST | `/api/v1/tasks/{task_id}/cancel` | `TaskSnapshot` | 首次 202 / 重复 200，前端未接 |
| 6 | POST | `/api/v1/tasks/{task_id}/retry` | `TaskCreatedResponse` | 需 `{item_ids}` + 幂等键，前端未接 |
| 7 | GET | `/api/v1/tasks/{task_id}/events` | SSE | 支持 `after` / `Last-Event-ID` |
| 8 | GET | `/api/v1/tasks/{task_id}/items/{item_id}/report` | `ReportResponse` | 未就绪 409 `REPORT_NOT_READY`，前端未接 |
| 9 | GET | `/api/v1/tasks/{task_id}/items/{item_id}/evidence` | `Page<EvidenceResponse>` | 支持 `claim_id/source_type/cursor/limit`，前端未接 |

SSE 事件仅 3 种：`task.status_changed`、`task_item.status_changed`、`task_item.node_progress`。

证据文件：`backend/src/insightx/api/v1/health.py`、`backend/src/insightx/api/v1/tasks.py`、`backend/src/insightx/api/router.py`。

## 3. 前端数据访问层实际状态

`frontend/src/api/client.ts` 只定义了 4 个函数，且全部是手写类型：

| client.ts 函数 | 对应后端 | 是否被业务调用 |
| --- | --- | --- |
| `createTask` | POST `/tasks` | ✅ `NewTaskDialog.vue` |
| `listTasks` | GET `/tasks` | ✅ `DashboardPage.vue` |
| `getTask` | GET `/tasks/{id}` | ❌ 无任何页面调用，且返回类型是 `unknown` |
| `cancelTask` | POST `/tasks/{id}/cancel` | ❌ 无任何页面调用，且返回类型是 `unknown` |

**完全没写调用封装的**：健康检查、`retryTask`、`getReport`、`listEvidence`。

`frontend/src/composables/` 只有 `useTaskList`、`useCreateTask`、`useTaskEvents`；缺 `useTaskDetail`、`useCancelTask`、`useRetryTask`、`useReport`、`useEvidence`。

**真正跑起来的业务请求只有 3 条**：创建任务、任务列表、SSE 事件流。

## 5. 缺口分类（关键）

### A. 后端已有、前端漏接（可直接补，无需后端改动）

| 后端接口 | 前端缺失物 |
| --- | --- |
| `GET /health` | 启动健康检查 / 顶栏状态点 |
| `GET /tasks/{id}` | `getTask` 类型补全 + `useTaskDetail` |
| `POST /tasks/{id}/cancel` | `useCancelTask` + 详情页操作按钮 |
| `POST /tasks/{id}/retry` | `retryTask` 封装 + `useRetryTask` + 分项勾选重试 |
| `GET .../report` | `getReport` + `useReport` |
| `GET .../evidence` | `listEvidence` + `useEvidence` |

### B. 前端页面本是静态占位（消费已有接口即可出数据）

- **雷达页**：任务批次表可直接用 `GET /tasks` 渲染，现在却是写死空态。
- **VOC / 改款页**：核心数据来自 `report` + `evidence`，接口已存在，等 Worker 产出后即可接。

### C. 后端确实未实现（P1/P2，`docs/api.md` §8 明确标注）

| 能力 | 成熟度 | 影响页面 |
| --- | --- | --- |
| 财务评估 | P1 未实现 | 财务风控页（当前恒 `NOT_EVALUATED`，符合边界） |
| 图片 / 视觉证据 | P1 未实现 | VOC 实拍画廊（`disabled`） |
| 工程任务书导出 | P1 未实现 | 改款页导出按钮（`disabled`） |
| 回测 | P2 未实现 | 无入口 |
| 跨平台扩展 | P2 未实现 | 雷达 BSR / 跨平台 tab（`disabled`） |
| 供应链能力 | P2 未实现 | 无入口 |

> `docs/api.md` §8 已定调：这些能力在验收口径冻结前，**不应为了「预留」而加空接口 / 空字段 / 未使用枚举**。前端当前用 `disabled` + 文案如实呈现，是正确做法。

### D. 文档与代码不一致（需修正，否则持续误导）

- `docs/前端设计.md` §4.2 写的是**旧契约**：`/api/v1/insight/task...`、6 个接口、`project_id` 字段、`stream.end` 事件、`task.updated` 等旧事件名 —— 这些在当前后端**都不存在**，属于已删除的历史实现。
- `docs/api.md` §6 的 `POST /tasks/{id}/retry` 等路径才是当前唯一基线。
- `client.ts` 的 `getTask` / `cancelTask` 返回 `unknown`，注释还写着「add when detail page exists」，属于半成品。

## 6. 为什么 Dashboard 仍然没数据（运行层面）

除了前端漏接，还有执行链路原因（`docs/api.md` §10 已记录）：

- Worker / outbox dispatcher / LangGraph **尚未接入**，新任务创建后长期停在 `QUEUED`。
- 节点执行 `run_node` 未实现 → 任务不会推进到 `RUNNING / COMPLETED`。
- 报告、证据是只读路由，**只有 Worker 接入后才会产生真实数据**；现在请求只会得到 `409 REPORT_NOT_READY` 或空分页。
- 因此 KPI、痛点、建议等需要报告聚合的模块，即使前端全部接上，也暂时只能渲染空态 —— 这是预期行为，不是 bug。

## 7. 建议补齐顺序

**第 1 步（纯前端，可立即做，不依赖 Worker）**

1. `client.ts` 补 `retryTask` / `getReport` / `listEvidence` / `health`，并把 `getTask`、`cancelTask` 从 `unknown` 换成真实类型（对齐 `backend/src/insightx/schemas.py`）。
2. `composables/` 补 `useTaskDetail` / `useCancelTask` / `useRetryTask` / `useReport` / `useEvidence`。
3. 雷达页「任务批次」接 `useTaskList`，替换写死空态。
4. Dashboard 的 `latestTaskId` 接 `useTaskDetail`，用快照驱动 KPI 与任务状态。

**第 2 步（依赖报告 / 证据产出）**

5. 新增任务详情页 / 报告页 / 证据抽屉路由，消费 `report` + `evidence`。
6. VOC、改款页从 report 数据取痛点、建议、证据链。

**第 3 步（工程与契约治理）**

7. 后端导出 `contracts/openapi.json` + `contracts/task-events.schema.json`，前端改为契约生成，停止维护两套手写 wire type（`docs/api.md` §11 已要求）。
8. 修正 `docs/前端设计.md` §4.2 / §5 的旧路径与旧事件名，避免继续误导实现。

**前置校验（联调前必须确认）**：Worker / 节点执行是否已能产出 `RUNNING → COMPLETED` 与真实报告、证据；否则第 2 步验收不了。
