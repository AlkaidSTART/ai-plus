## 1. 总体结论

InsightX 的“评论样本 → 痛点归纳 → 产品本体/包装履约双栏建议 → 证据回查”主线有条件可行。Vue + FastAPI + LangGraph + PostgreSQL/pgvector 无需整体更换。

当前需要优先解决的不是增加页面或扩大 Agent 数量，而是三个前置条件：可持续取得原始评论、使用可调用且经过样本评估的模型、让分析结果具备明确的来源与适用边界。

原方案中的“任意 ASIN 获取 200–500 条评论”“从买家图片精确判定物理成因”“全链路 30–60 秒”“精确 FBA 降档和收益预测”不能仅凭技术选型视为已经可兑现的交付承诺。应分别转为数据源验收、视觉评估、性能基线和费用模型校验。

本文区分四类结论：**官方已确认**是公开产品/API 能力；**源码已观察**是当前实现事实；**修正建议**是本次提出的工程方案；**待实测**需要真实账号、样本或运行环境才能确认。公开能力不等于当前账号有权限，也不等于本项目已经集成成功。

## 3. 联网可行性核验

### 3.1 Amazon 评论与买家图片：需要独立数据源验收

**官方已确认：** Amazon Customer Feedback API 提供聚合评论/退货洞察，数据每周更新，输出仅英语；ASIN 教程提供正面、负面各最多 10 个主题及月度主题趋势。它不是批量原始评论导出接口。[Amazon 总览](https://developer-docs.amazon/sp-api/lang-en_US/docs/customer-feedback-api)、[ASIN 洞察教程](https://developer-docs.amazon/sp-api/lang-US/docs/get-feedback-insights-asin)

官方模型中的主题包含有限数量的文本片段，主题的 `reviewSnippets` 最多 3 条；其返回结构不提供本项目要求的逐条评论 ID、日期、星级和买家图片关联。因此，这个接口无法直接替代 PRD 的原始评论证据管道。[Amazon 官方 OpenAPI 模型](https://raw.githubusercontent.com/amzn/selling-partner-api-models/main/models/customer-feedback-api-model/customerFeedback_2024-06-01.json)

**权限边界：** 调用需要所服务 selling partner 的授权及相应角色；教程区分 seller 的 Selling Partner Insights 与 vendor 的 Brand Analytics。不能据此自行推定“所有竞品都能读”或“只允许自己的商品”；目标 ASIN 是否有数据，应由获授权账号验证。[官方权限前提](https://developer-docs.amazon/sp-api/lang-US/docs/get-feedback-insights-asin)

**修正建议：** 原始评论、聚合主题、价格历史分开接入，保存其不同来源和覆盖范围。Amazon 聚合主题可作为补充验证，不能伪装成自采原文。

### 3.2 Keepa 与商业评论服务：分清数据职责

**官方已确认：** Keepa Product Object 面向商品背景、价格历史等数据；`reviews` 对象描述评分数/评论数时序，`images` 是商品轮播图。字段名字不能作为“已获取评论正文和买家图”的依据。[Keepa Product Object](https://keepa.com/api-docs/product-object.html)

**候选但未验收：** Rainforest 厂商产品页声明提供评论文本、星级、图片等信息，通用参数文档列出 `type=reviews`。本次未完成其评论专用参数/结果页核验：研究时相关页面返回未找到或无法读取，未确认当前分页上限和字段稳定性。因此仅列为试采候选，不作为采购决定或覆盖率保证。[Rainforest 产品说明](https://trajectdata.com/ecommerce/rainforest-api/)、[通用参数文档](https://docs.trajectdata.com/rainforestapi/product-data-api/parameters/common)

**修正建议：** 不再把“Keepa / RapidAPI”当作已完成的数据选型；应记录具体服务、接口版本、授权方式、字段契约、返回限制、留存使用条件、费用和失败计费规则。当前后端 `/amazon/product`、`/amazon/reviews` 是项目预设网关协议，不是所有厂商通用协议。

### 3.3 Claude：文档模型已过期，结构化输出可改进

**官方已确认：** Anthropic API 的 `claude-3-7-sonnet-20250219` 已于 2026-02-19 退役，`claude-3-opus-20240229` 已于 2026-01-05 退役；对退役模型的请求会失败。本结论针对 Anthropic 自营 API，不能直接套用其他云平台的生命周期。[模型退役记录](https://platform.claude.com/docs/en/about-claude/model-deprecations)

**修正建议：** 后续统一修改文档示例中的退役 ID，候选基线可采用官方当前列为 Active 的 `claude-sonnet-4-6`，最终以目标账号可调用性、样本质量和单任务成本确定。当前代码默认 Sonnet 4.5 与文档不同，应一并建立替换日期、回归样本和配置记录；本次不直接改模型配置。

官方已提供 JSON Schema 结构化输出和严格工具输入能力，可用于替代仅靠提示词、正则抽取 JSON 的主路径；仍须处理拒绝、输出截断和本地业务校验。字段符合 Schema 不代表建议事实正确。[Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

原技术方案的“Prompt Caching 固定降低 80% 成本”改为待测目标。缓存有写入、读取等不同计费条件，实际收益取决于复用前缀与命中情况；按选定模型的当期计费和实际 usage 计算。[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

### 3.4 多模态取证：适合缺陷线索，不应默认保证精确归因

**官方已确认：** Claude 支持图片理解，但官方明确指出低质量图片可能导致错误，坐标和定位输出为近似值。[Vision 能力与限制](https://platform.claude.com/docs/en/build-with-claude/vision)

**基于上述限制的推断与建议：** 买家图片可支撑“疑似断裂、包装破损、可见色差”等辅助判断；单张图不能默认证明模具公差、材质等级或加工尺寸。P1 输出应区分可见现象、模型推断和待工程确认事项；毫米级改动必须说明依据与人工确认要求。

边界框应记录图片原始尺寸、模型输入尺寸及坐标换算；缺少可靠定位时返回空值和原因，不用零面积框制造已完成标注的假象。模型给出的 `confidence` 未经评估不应称为统计校准后的准确率。

### 3.5 BGE-M3 与 pgvector：选型可行，质量和速度仍需测试

**官方已确认：** BGE-M3 提供 1024 维表示、最长 8192 输入长度，并支持 Dense、Sparse 和多向量路线；模型卡提供多语言检索用途。[BGE-M3 模型卡](https://huggingface.co/BAAI/bge-m3)

pgvector 的 HNSW `vector` 索引支持至 2000 维，能容纳 1024 维向量；混合检索需要额外结合全文检索与结果融合。向量近邻搜索本身不等于评论痛点聚类。[pgvector 官方说明](https://github.com/pgvector/pgvector)

**修正建议：** P0 明确实施 Dense 语义表示与独立聚类逻辑；Sparse/BM25 融合待检索评测证明必要后再加入。当前聚类应校验质心归一化、输入顺序敏感性、无差评样本和跨语言标签质量；Fake Embedding 只允许演示与测试。

### 3.6 任务调度、恢复与部署：需要补齐运行语义

**官方已确认：** LangGraph 在配置 checkpointer 后可保存图状态并按 thread 恢复。数据库里保存任务列表，与保存可恢复的图执行状态是两件事。[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

FastAPI 官方将 Celery 等队列工具列为重计算、多进程/多机器任务的可选路径；多 worker 进程通常各自占用模型内存，不能把进程内单例视为全服务唯一实例。[后台任务说明](https://fastapi.tiangolo.com/tutorial/background-tasks/)、[部署与进程内存](https://fastapi.tiangolo.com/deployment/concepts/)

**修正建议：** 本地演示可以保留单进程执行；正式并发路径落实原方案已有的 Celery worker 和持久化恢复设计。队列负责投递、并发和重试，checkpointer 负责图恢复，数据库负责业务结果；明确各自边界，不保证外部调用天然只执行一次。

核心结果写入应在任务完成之前确认成功。当前 `real_providers.py` 存在后台尽力写入逻辑，应测试它与最终报告落库的时序，避免状态完成但报告缺项。

### 3.7 SSE 与 Vite：可实现，需统一协议与构建配置

**官方已确认：** EventSource 支持重连和 `Last-Event-ID`；原生构造参数只有 URL 与 credentials 选项，没有任意 Authorization header 配置入口。[WHATWG SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html)

**修正建议：** P0 单租户演示与 P1 JWT 鉴权分开描述。P1 若保持 Bearer 契约，使用可携带请求头的流式请求实现并负责重连；若选择 Cookie 会话，应同步修改鉴权契约。不能把长期访问令牌直接拼到 SSE URL。

统一 `message` 字段与 `COMPLETED / FAILED / CANCELED` 终态；最近事件重放与按游标续传应明确区别。当前后端已有取消终态和最近事件重放，应优先同步文档并补测，而不是重复实现。

Vite 的 `import.meta.env` 在构建时静态替换。运行静态容器时设置环境变量，不会自动更新已经构建的 JS；应选择构建时注入或明确的运行时配置方案。[Vite 环境变量说明](https://vite.dev/guide/env-and-mode)

### 3.8 财务与 FBA：只能在明确假设下做估算

**官方已确认：** FBA 成本与商品尺寸、重量等有关；Amazon 提供费用预估工具。Product Fees API 返回估计费用，实际费用可能不同。[Amazon FBA](https://sell.amazon.com/fulfillment-by-amazon)、[Product Fees API](https://developer-docs.amazon.com/sp-api/reference/getmyfeesestimateforsku)

**修正建议：** 当前仅用体积重分档和固定金额的代码不能代表完整的官方计费规则。应记录站点、费用生效日期、品类、包装尺寸、实际重量及所用估费来源；拟议包装改动先做版本化费表情景模拟，不能默认已有 ASIN 的估费接口能测算任意新包装。

财务计算保留确定性规则，但需要显式输入月销量、原始退货率、退货改善的相对/绝对定义、每次退货净损失、一次性投入、持续单件增量成本及计算周期。当前 `monthly_units()` 默认 1000 和简化收益公式应在演示中显式披露，不能悄悄充当真实经营数据。

本文件不提供新的官方费率或已经验证的收益预测；后续以选定市场当期费用资料、实际输入及可复算示例验收。

### 3.9 依赖版本：已确认存在，不等于完成兼容性验证

本次查到 PyPI 上确有 FastAPI 0.141.1 和 LangGraph 1.2.11 的发布文件。保留现有版本路线，不因旧知识误判版本不存在；完整兼容性仍以锁文件安装、Python 3.12 环境和相关测试为准。[FastAPI 发布](https://pypi.org/project/fastapi/0.141.1/)、[LangGraph 发布](https://pypi.org/project/langgraph/1.2.11/)

缓存约定也需细化：不能只按 ASIN 判定复用；至少考虑站点、来源、时间窗、样本上限/筛选、快照版本。数据缓存命中与重复创建任务的幂等性分开定义，同样的原始数据可以在不同成本参数下生成不同报告。

## 5. 修正后的实施顺序

按“前一阶段拿出证据，后一阶段再扩大能力”执行。下表是建议顺序和角色分工，不是已承诺工期；原 40 天排期应在数据源试采与首次真实运行后重新估算。前端契约联调可以与数据源验证并行，真实能力验收不能绕过数据验证。

| 阶段 | 目标与工作 | 建议责任角色 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- | --- |
| A：数据与模型验证 | 从目标品类选择 5–10 个 child ASIN；验证原文、图片关联、分页、时间覆盖、费用；验证替代模型可调用性 | 后端/数据、AI、产品 | 数据字段对照、实际样本、模型小样结果、每次任务成本记录 | 有可追溯原始样本；账号与数据使用条件明确；模型输出能被解析和复核 |
| B：文本主链路 | 统一 P0 契约；复用现有采集/清洗/聚类/建议服务；关闭未验收能力；补充证据关联和真实模式检查 | 后端、AI | 原始样本到双栏报告的真实执行记录；未评估/降级状态 | 不依赖 Fake Embedding；无凭空证据；正常、空数据与上游失败路径可解释 |
| C：前后端闭环 | 使用真实 API 替换当前 mock 数据绑定；接任务提交、进度、报告和证据抽屉；修复环境与字段差异 | 前端、后端 | 可操作 Demo、接口回归记录、构建结果 | 实际提交产生后端任务；刷新可查任务；完成/失败/取消和证据回查正常 |
| D：可靠运行与基线 | 落实持久化与 worker；核验结果写入；测冷启动、热启动、并发、重连、重启、限流和费用 | 后端、测试/部署 | 部署清单、故障恢复记录、性能与费用基线 | 不丢核心报告；状态最终一致；能说明任务吞吐与单任务成本 |
| E：P1 能力 | 小规模图片取证与坐标验收；明确财务输入和费用规则；完善账户权限 | AI、后端、产品/业务复核 | 图像评估样本、财务复算账本、权限测试 | 视觉与财务各自通过验收，再显示为可用功能 |
| F：P2 扩展 | 先取得历史快照和平台数据，再实现回测、SKU 映射、供应链告警 | 数据、AI、产品 | 防止未来信息泄漏的回测集、平台匹配评估 | 历史数据时点可信；指标定义清楚；不能只用演示样例证明效果 |

如果阶段 A 暂时拿不到在线原始评论，可以使用已获得使用许可、保留来源的本地样本验证 B/C，并标记为“快照回放”。这只能证明分析和交互链路，不代表在线采集已经完成；不因此新增无关平台或整套上传产品功能。

## 6. 验收与测量方式

### 6.1 数据验收

建议以 5–10 个 ASIN 作为探索集，不据此宣称大盘覆盖率。逐个记录请求数量、实际返回量、有效去重量、最早/最晚日期、星级与语言分布、父子变体、图片可访问情况、采集耗时与费用。区分上游无数据、产品本来评论不足和系统错误。

200–500 条保留为样本目标；95% 成功率只有在定义“成功”的条件、样本集和观察周期后才有意义。样本不足时返回实际数量及覆盖限制，禁止补造评论。所有聚合占比注明分母，精选差评样本不能被标为全商品差评率。

### 6.2 分析质量

建议先由业务人员标注约 100 条目标品类评论作为探索集，再独立保留验收集；样本规模是本次工作建议，不是已证明足够的统计结论。

检查跨语言同义问题是否聚合、产品与包装归因是否区分、无痛点时是否错误强造 Top 5、每条建议是否引用真实证据。允许少于 5 个有证据的痛点。严重度的评分规则与工程风险分开解释，不把低星级直接等同于物理危险。

对证据引用执行硬性检查：被引用 ID 必须存在，引用文本必须来自已取得样本；人工抽查建议是否真的由对应证据支持。质量阈值由首轮标注结果和业务容忍度确定，不预先填未经验证的“准确率”。

### 6.3 性能和成本

原 PRD 指标保留为待验证目标，不宣称已达到：

| 指标 | 测量条件必须包含 | 本次修正 |
| --- | --- | --- |
| 基础查询 P95 ≤200ms | 环境、并发数、数据库规模、冷热缓存、是否含网络 | 排除模型长任务和 SSE 存活时长，单独测量查询 |
| 单 ASIN 全链路 30–60s | 采集是否命中缓存、评论长度/数量、图片数量、模型/设备、限流与重试 | 冷采集、热样本、含视觉三种分别统计 P50/P95；当前逐图串行流程不能被当作已满足此目标 |
| 10 万评论检索 ≤50ms | 索引、过滤条件、召回量、硬件与查询集 | 除延迟外记录召回质量；不把内存聚类时间混为数据库检索时间 |
| SSE 延迟 ≤300ms | 后端事件生成时间、浏览器接收时间、代理与连接数 | 测端到端延迟、断线续传与终态，不只测函数耗时 |
| 模型/采集成本 | 实际 token、图片、缓存读写、数据源计费、失败重试 | 输出“每次完成分析的实际成本”，不用固定缓存折扣替代测量 |

建议先测 1、3、10 个并发任务；记录进程数和每个进程的模型内存占用，避免把本地单例误当作多进程共享。不得从 PyPI 版本存在或框架文档推导本项目满足 SLA。

### 6.4 状态、降级与财务

必须覆盖：数据为空、网关限流、模型不可用、结构化输出无效、Vision 失败但文本可继续、缺 Embedding、取消、财务否决、重试耗尽、SSE 断线和进程重启。演示成功、文本降级成功、财务否决报告和技术失败分别可识别。

财务验收至少覆盖零销量、未知销量、零/负净收益、一次性成本、持续单件成本、回本周期超阈值、改款后费用不降反升。将“无足够数据”与“零成本/零风险”分开，不以占位默认值自动得出通过结论。
