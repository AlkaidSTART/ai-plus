# 后端开发路线图与任务拆分：实施计划

## 目标

在不改动后端业务代码、不恢复当前工作区中已删除的历史文件的前提下，建立根目录 `plan/` 下的后端分阶段路线图。路线图使用统一三位序号目录（`001-` 至 `016-`），每个目录只创建一个 `plan.md`，明确阶段目标、前置条件、边界、实施任务、验证门槛、风险和未开始状态。

路线图须覆盖 InsightX 的 M0、P0、P1、P2 和最终部署保障，并使 P0 的最小闭环可以按依赖顺序实施：真实数据/云端模型验证 → 后端基础设施 → 安全与任务可靠性 → 采集/分析/报告 → 联调验收。

## 当前事实及依据

- 根目录 `README.md`、`PRD.md` 与 `docs/architecture.md` 均明确：当前工作区处于设计文档阶段，**没有可运行的前后端实现、依赖清单、数据库、模型接入或 CI**。目标后端为 Python 3.12、uv、FastAPI、Pydantic 2、SQLAlchemy 2、psycopg 3、Alembic、PostgreSQL/pgvector、Celery/Redis、事务 outbox、LangGraph/PostgreSQL checkpointer。
- `PRD.md` 将 P0 限定为 Amazon US 文本闭环；P1 是视觉取证与确定性财务否决；P2 是回测、跨平台映射与供应链信号。M0-A 的数据来源、云端 LLM/Embedding（以及单列的 VLM）验证是后续真实链路的前置门禁。
- `docs/architecture.md` 规定：前后端仅经 REST + SSE 通信；后端 DTO 是 OpenAPI/事件 schema 的单一来源；PostgreSQL 是任务、报告、证据和有序事件的事实源；Worker 的云端调用不应在 HTTP 请求或长数据库事务中执行。
- 当前 `git status --short` 显示 `backend/`、`frontend/`、旧 `plan/00-` 至 `plan/14-` 等 127 个已跟踪文件均处于未暂存删除状态；根目录当前也没有 `plan/`。本任务不恢复、重命名、覆盖或解释这些用户现有删除。
- Git `HEAD` 中有历史后端快照，但它采用异步 SQLAlchemy、数据库轮询 worker、旧 `/api/v1/insight/...` 路径，且当前工作区已删除。它与当前目标的同步 SQLAlchemy、Celery/outbox、LangGraph 和拟定 `/api/v1/tasks` 资源路径不一致，只可作为历史证据，不能作为本路线图的可运行基线。
- 当前环境检测到 Node.js `v24.20.0` 与 Bun `1.4.2`，未检测到 `uv`、Docker、Docker Compose 或 `psql`；尚未提供数据源授权、模型账户、预算、模型 ID、区域或财务规则。路线图将这些列为门禁，而非已满足条件。
- 根目录 `AGENTS.md` 要求每项实际实施另在 `docs/plans/YYYY-MM-DD-<任务简称>/` 先写可审核计划、展示并等待明确批准，完成后单独写 `result.md`。根目录 `plan/` 的阶段路线图不能替代该审批流程，也不构成对任何代码、依赖、迁移、外部调用、部署或付费操作的授权。

## 实施步骤与分工

1. 向用户展示本计划、当前事实、拟定的 16 个阶段目录和关键依赖，停止等待明确批准。用户的本次需求不视为对尚未展示计划的批准。
2. 获批后，在本文件的审核状态中记录真实日期和用户原文，并重新检查 Git 工作区；若目标变为迁移/恢复旧 `plan/00-` 至 `plan/14-`，或要求同时修改代码、文档架构或历史文件，先修订本计划并重新审核。
3. 创建 `plan/001-` 至 `plan/016-` 目录及各自唯一的 `plan.md`。所有阶段文档统一包含：目标、前置条件、范围与非范围、计划任务、验收/验证、风险与待决项、阶段状态。
4. 在 `001` 中记录依赖关系和执行规约；在其余阶段中只计划对应范围，不把 P1/P2 或部署工作提前混入 P0 任务。明确 M0 与外部数据/付费云调用的审批门禁。
5. 所有阶段文档均写明：执行该阶段前必须另建对应的 `docs/plans/YYYY-MM-DD-<任务简称>/plan.md`、展示并取得单独批准；阶段完成后才在该阶段目录写实际的 `result.md`。本次不创建这些结果文件。
6. 回读全部新文件，执行文档结构、命名、依赖与范围检查；随后在本任务目录生成独立 `result.md`，如实记录创建结果、验证和未执行的项目运行检查。

分工：当前会话没有可直接调用的子代理，且 `paseo` CLI 不存在；由主代理完成只读分析、路线图编写和文档核对。不会为形式化分工安装工具、创建外部服务或启动额外代理。

## 验证与验收

获批后的计划文档验证包括：

- `find plan -mindepth 2 -maxdepth 2 -name plan.md` 与目录名检查：恰有 16 个 `plan.md`，目录名按 `001-` 至 `016-` 连续且不存在旧两位序号的新建目录。
- 逐个完整回读 `plan/*/plan.md`：确认均包含目标、依赖/前置、范围、任务、验证、风险和“未实施/须另行审批”状态；`001` 的导航与各阶段名称/依赖一致。
- 文本检查：无行尾空白、Markdown 围栏和表格闭合、内部相对链接（如存在）可解析；不安装 Markdown 渲染器，不把文本检查说成浏览器渲染验收。
- `git diff --check` 与 `git status --short`：确认新增范围仅为本任务 `docs/plans/...` 记录和根目录 `plan/001-` 至 `plan/016-`，且任务开始前已有的删除、修改和未跟踪文件保持原样；不暂存、提交或恢复文件。
- 不运行应用、依赖安装、迁移、容器、真实采集或云端模型调用：当前工作区没有后端实现，且这些均属于后续单阶段实施及外部审批范围。

验收条件：用户可以从 `001` 获得完整后端实施顺序和依赖，从每个三位编号目录获得可独立立项的最小范围；P0/P1/P2 边界、M0 外部验证门禁、历史快照不可直接复用、以及每阶段的独立审批要求均清楚可见。

## 风险与非目标

- 本任务创建的是路线图文档，**不是**后端实现、旧计划迁移、代码恢复或任何阶段的批准；不能据此声称 P0/P1/P2 已实现。
- 当前工作树存在大量用户现有删除。按“新建”理解，本任务只新建三位编号计划，不重写或恢复 Git 历史中的两位编号计划；若用户实际需要重编号迁移历史，请先修改范围并重新审核。
- 数据采集授权、供应商账户、密钥、可用区域、模型 ID、费用、数据处理条款、真实 PostgreSQL/pgvector 兼容性和财务规则尚未确认。路线图只能设置验证门禁，不能虚构结论。
- 仅有规划文件不保证阶段估时或交付日期；不创建甘特图、人员承诺、预算、CI、脚手架、依赖、数据库或容器。
- 当前环境未发现 `uv`、Docker、Docker Compose、`psql`，但本任务不安装它们。环境准备在经批准的 `003` 阶段处理。
